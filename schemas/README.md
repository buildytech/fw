# FW schemas

Canonical, versioned documents for `schemaVersion: urn:fwyml:manifest:v0alpha1`.

`fwyml` may pin copies for offline parse. This directory remains the source
of truth. None of these schemas name a product vertical.

| File | Kind |
| --- | --- |
| `product-manifest.schema.json` | user `fw.yaml` |
| `registry-envelope.schema.json` | registry index and records |
| `lock.schema.json` | resolved snapshot |
| `harness-result.schema.json` | command report |

Registry kinds are listed in `registry-kinds.md`.

## Compatibility and reproducibility extensions

`Product.composition.capabilities.<port>.contractRange` expresses the
contract range a chosen adapter must satisfy. Product constraints are
evaluated from registry record ids, provided capabilities, features, platforms,
and runtimes; they never cause product or stack branches in the compiler.

`Lock` binds the semantic manifest, all loaded registry documents, and the
materialization plan through SHA-256 digests. It also stores per-output
ownership digests, so reconciliation can remove only unchanged formerly owned
files. Locks created before these fields existed are intentionally stale and
must be regenerated by `fwyml sync`.

An npm source that should enter a product dependency graph declares an exact
`source.ref` and an explicit `source.install` scope. The compiler does not
invent a package version from an adapter id or use an unpinned package source.

The bundled schemas in `fwyml` are offline parser copies. They must remain
byte-for-byte compatible with these canonical documents.
